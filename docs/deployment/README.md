# Deployment Guide

This app is designed to deploy as three independent pieces:

| Piece | Where | Why |
|---|---|---|
| Frontend (Next.js) | [Vercel](https://vercel.com) | Zero-config Next.js hosting, generous free tier |
| Backend (Express) | [Render](https://render.com) | Free web service with Docker support and a health-check path |
| Database | [MongoDB Atlas](https://www.mongodb.com/atlas) | Free (M0) managed MongoDB cluster |

Docker/`docker-compose.yml` is provided for **local development** and as a
self-hostable alternative to Render — it isn't the primary production path.

## 1. MongoDB Atlas

1. Create a free account and an M0 (free tier) cluster.
2. Under **Database Access**, create a user with a password (avoid special
   characters that need URL-encoding, or encode them if you use them).
3. Under **Network Access**, add `0.0.0.0/0` (allow from anywhere) — Render's
   IPs aren't static on the free plan, so IP allowlisting isn't practical here.
4. Copy the connection string from **Connect → Drivers**. It looks like:
   `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?appName=<name>`
   This is your `MONGODB_URI`.

## 2. Backend on Render

### Option A — Blueprint (recommended)

The repo includes [`render.yaml`](../../render.yaml) at the root. In Render:

1. **New → Blueprint**, connect this GitHub repo.
2. Render reads `render.yaml` and provisions a Docker-based web service
   (built from `backend/Dockerfile`) with a `/health` health check.
3. Before the first deploy completes, set the two secrets Render won't fill
   in automatically (`sync: false` in the blueprint):
   - `MONGODB_URI` — the Atlas connection string from step 1
   - `GEMINI_API_KEY` — get a free key at
     [aistudio.google.com/app/apikey](https://aistudio.google.com/app/apikey)
     (optional — leave blank to run on the deterministic mock AI provider)
4. `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are auto-generated by Render
   (`generateValue: true`) — you don't need to set these.

### Option B — Manual web service

If blueprint sync isn't available on your plan, or Render's blueprint schema
has moved on since this was written:

1. **New → Web Service**, connect the repo.
2. Runtime: **Docker**. Root/context directory: `backend`. Dockerfile path:
   `backend/Dockerfile`.
3. Health check path: `/health`.
4. Add the environment variables listed in the [reference table](#environment-variables-reference)
   below under **Backend**.

Once deployed, note the service URL (e.g. `https://ai-travel-planner-backend.onrender.com`)
— the frontend needs it in the next step.

## 3. Frontend on Vercel

This is a monorepo with the Next.js app in `frontend/`, not at the repo root,
so the one non-default setting is the project root:

1. **Add New → Project**, import this GitHub repo.
2. In the import screen (or **Settings → General** after creating the
   project), set **Root Directory** to `frontend`.
3. Framework preset should auto-detect as **Next.js** — leave build/output
   settings on their defaults.
4. Under **Settings → Environment Variables**, add:
   - `BACKEND_URL` = your Render backend URL from step 2 (e.g.
     `https://ai-travel-planner-backend.onrender.com`, no trailing slash)
5. Deploy.

### Why `BACKEND_URL` and not a public API URL

`next.config.ts` proxies `/api/*` through a Next.js rewrite to `BACKEND_URL`
server-side, so the browser only ever talks to the frontend's own origin.
This matters because the backend's refresh-token cookie is `SameSite=strict`
— on two genuinely different domains (`*.vercel.app` and `*.onrender.com`)
that cookie would never be sent, silently breaking session refresh. Routing
through the rewrite makes every request same-origin from the browser's point
of view, so the cookie works normally. Don't route around this proxy by
pointing the frontend directly at the backend's public URL.

## 4. Verify

- Backend: `GET https://<your-render-url>/health` → `{"success":true,"database":"connected",...}`
- Frontend: open the Vercel URL, register an account, and create a trip. If
  trip creation hangs or 502s, check the Render service logs — the most
  common cause is a missing/invalid `MONGODB_URI` or Atlas network access
  rule.

## Local development with Docker Compose

`docker-compose.yml` at the repo root spins up all three pieces locally,
using a containerized MongoDB instead of Atlas:

```bash
docker compose up --build
```

- Frontend: http://localhost:3000
- Backend: http://localhost:5000
- Mongo: `mongodb://localhost:27017` (data persisted in the `mongo-data` volume)

The backend service overrides `MONGODB_URI` to point at the local `mongo`
container regardless of what's in `backend/.env`, so this never touches your
real Atlas cluster. The frontend's `BACKEND_URL` is a Docker build arg
(baked in at `next build` time — see the note in `docker-compose.yml`), so
if you change it you need `docker compose build frontend` again, not just a
restart.

To run just the backend against your own `.env` (e.g. against real Atlas),
use `docker compose up backend` after removing the `MONGODB_URI` override
in `docker-compose.yml`, or simply run `npm run dev` in `backend/` instead —
Docker Compose here is for full-stack local testing, not required for
day-to-day development.

## CI

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) runs on every
push and PR to `main`: backend (typecheck, Jest + Supertest against an
in-memory MongoDB, build) and frontend (lint, typecheck, Jest + React
Testing Library, build) run as two parallel jobs. Nothing is deployed from
CI — Vercel and Render both deploy independently on push via their own
GitHub integrations once connected.

## Environment variables reference

### Backend (Render / `backend/.env`)

| Variable | Required | Notes |
|---|---|---|
| `NODE_ENV` | yes | `production` on Render, `development` locally |
| `PORT` | yes | `5000` |
| `MONGODB_URI` | yes | Atlas connection string |
| `JWT_ACCESS_SECRET` | yes | ≥32 chars; Render can auto-generate |
| `JWT_REFRESH_SECRET` | yes | ≥32 chars; Render can auto-generate |
| `ACCESS_TOKEN_EXPIRES_IN` | yes | e.g. `15m` |
| `REFRESH_TOKEN_EXPIRES_IN` | yes | e.g. `7d` |
| `GEMINI_API_KEY` | no | omit to use the mock AI provider |
| `GEMINI_MODEL` | no | defaults to `gemini-flash-latest` |
| `AI_PROVIDER` | no | `gemini` \| `mock`; auto-detected from `GEMINI_API_KEY` if omitted |

### Frontend (Vercel / `frontend/.env.local`)

| Variable | Required | Notes |
|---|---|---|
| `BACKEND_URL` | yes | Backend origin, used server-side by the `/api/*` rewrite |
